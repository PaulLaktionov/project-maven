# Racer Game — Maven Fat-JAR Build

A JavaFX racing game packaged into a single runnable **fat JAR** using only Maven configuration.

The game code comes from the course template (fork of [vasylmalik/project-maven](https://github.com/vasylmalik/project-maven)). **My part of the work is the build:** I configured `pom.xml` so that one command compiles the game, runs the tests, collects all dependencies and packs everything into one JAR that starts with `java -jar`.

## Download & Play (Windows)

No Java, no console needed:

1. Open **[Releases](../../releases)** and download `RacerGame.zip`.
2. Unzip it anywhere.
3. Double-click **`RacerGame.exe`**.

The app comes with its own Java runtime built in, so nothing else has to be installed.

## Tech stack

- Java 18 (JDK 18.0.1)
- Maven
- JavaFX 18
- JUnit 5
- JavaRush desktop game engine (local JAR, not available in Maven Central)

## What I configured

| Task | How it is solved in `pom.xml` | Phase |
|---|---|---|
| Install the local game engine JAR from `lib/` into the local Maven repository | `maven-install-plugin`, goal `install-file` | `validate` |
| Compile the project | `maven-compiler-plugin`, Java 18 via `maven.compiler.source/target` | `compile` |
| Skip one broken test (`StrangeTest`) and keep the rest running | `maven-surefire-plugin` with `<excludes>` | `test` |
| Copy all `compile`-scope dependencies into one folder | `maven-dependency-plugin`, goal `copy-dependencies` → `target/lib` | `generate-resources` |
| Put the collected dependency JARs inside the final JAR under `lib/` | `<resources>` section: `target/lib` → `lib` | `process-resources` |
| Make the JAR runnable | `maven-jar-plugin` with a custom `MANIFEST.MF` | `package` |

### The manifest

```
Main-Class:      org.eclipse.jdt.internal.jarinjarloader.JarRsrcLoader
Rsrc-Main-Class: com.javarush.games.racer.RacerGame
Class-Path:      lib/*.jar  (generated by Maven) + ./
```

- `Main-Class` is a custom class loader that can load classes from JARs *inside* a JAR and start a JavaFX application.
- `Rsrc-Main-Class` is the real entry point of the game, which the loader starts.
- `Class-Path` is generated automatically (`addClasspath` + `classpathPrefix lib/`), so the dependency list never has to be maintained by hand.

## Build and run

```bash
# build: installs the engine, compiles, tests, packs the fat JAR
mvn clean install

# run the game through Maven (for development)
mvn javafx:run

# run the packaged fat JAR
"<path to JDK 18>/bin/java" -jar target/project-maven-1.0.jar
```

> On Windows PowerShell, start the command with `&`: `& "C:\...\java.exe" -jar target/project-maven-1.0.jar`

### Packaging into a native app (no Java required)

The fat JAR is wrapped into a standalone Windows application with `jpackage`, which ships with the JDK. The result is a folder with `RacerGame.exe` and a bundled Java runtime.

```powershell
# 1. build the fat JAR
mvn clean install

# 2. put only the JAR into a separate folder, so jpackage doesn't copy the whole target/
mkdir app
copy target\project-maven-1.0.jar app\

# 3. wrap it into an app with its own runtime
& "<path to JDK 18>\bin\jpackage.exe" --type app-image --name RacerGame --input app --main-jar project-maven-1.0.jar --dest dist
```

`dist\RacerGame\` is then zipped and attached to a GitHub Release. The main class is taken from the JAR's `MANIFEST.MF`, so it doesn't have to be passed to `jpackage`.

> Both the JAR and the app are platform-specific: JavaFX ships native libraries, so a build made on Windows runs on Windows, not on macOS or Linux.

## Problems I ran into and solved

- **Chicken-and-egg with the local dependency.** Maven resolves dependencies before most plugins run, so the game engine has to be installed in the very first phase (`validate`). Otherwise the build fails because the dependency is not there yet.
- **Phase order matters.** Dependencies must be copied (`generate-resources`) *before* resources are processed, or the final JAR ends up without `lib/`.
- **A failing test blocks packaging.** `package` runs every earlier phase, including `test`, so the broken test had to be excluded before the JAR configuration could even be checked.
- **`ClassNotFoundException` on start.** The loader also needs the root of the JAR on its classpath, so `./` was added to `Class-Path` next to the generated `lib/` entries.
- **IDE vs terminal mismatch.** IntelliJ's bundled Maven used a different local repository than the Maven in the terminal, so the IDE could not see the installed engine until both pointed to the same repository.

## What I learned

- The Maven build lifecycle and how to bind a plugin goal to a specific phase
- The difference between dependencies (used by the code) and plugins (used by the build)
- How a runnable JAR works: `MANIFEST.MF`, `Main-Class`, `Class-Path`
- Packing dependencies into a single distributable file
- Excluding tests in Surefire without disabling the test phase
- Reading Maven error output to find the actual cause
- Shipping a Java desktop app to users without Java installed, using `jpackage` and GitHub Releases
